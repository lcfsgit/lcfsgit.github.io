起因

听起来就是个数数的事。但数据量一上来，问题就一个接一个。

最初的做法，和它是怎么崩的

第一版代码写得很”理所当然”：

跑了一下，三个问题同时炸了：

  1. 内存直接打爆。400 万条 _source 全塞进一个 list，单机内存吃紧，跑到后半段 OOM 了。
  2. Scroll 上下文超时。中间网络抖了一下，scroll_id 失效，400 万条从头再来。
  3. 太慢。scroll 本身要维护快照上下文，越往后越慢，跑完一次全量将近两小时。

这不是优化能解决的问题，是方案本身就不对。

重新想这件事

坐下来理了一下，这个任务本质上就两件事：

  • 离线阶段：把 400 万条数据过一遍，构建每个指标的全局有序数组。
  • 在线阶段：来一条数据，在有序数组里二分查找，算出百分位。

在线阶段其实没什么好优化的——bisect_right 在 400 万长度的数组里查一次也就二十几次比较，微秒级的事。瓶颈全在离线阶段：怎么又快又稳地把 400 万条数据从 ES 里搬出来，构建好有序数组。

所以问题收敛成：怎么可靠地、低内存地、可中断恢复地从 ES 拉取 400 万条数据。

第一件事：扔掉 Scroll，换成 search_after

Scroll API 的设计初衷是做短时间内的批量导出，它会在服务端维护一个快照上下文。这个上下文是有状态的——占内存、有超时时间、阻止段合并。400 万条数据要拉很久，scroll 上下文扛不住。

search_after 是无状态的。原理很简单：每次查询带上一页最后一条数据的排序值，ES 根据这个值定位下一页的起点。服务端不保留任何上下文。

切到 search_after 之后，最大的好处不是速度，是心安。不用惦记 scroll 上下文过没过期，不用在低峰期赶时间跑完。它就是一个普通的查询，失败了重试当前页就行。

之前的代码把所有 _source 攒到 list 里再处理，400 万条 × 每条大概 1~2KB，内存直接吃掉好几个 G。

第三件事：加一层 Redis，让进程可以”死而复生”

流式拉取解决了内存问题，但还有一个隐患：进程要是挂了怎么办？400 万条跑了 380 万，突然被 kill 了，从头来？

重启之后，进程读 Redis 拿到上次的游标，接着跑。不会重复，不会遗漏。

最终方案一览

把上面四件事串起来，整个流程是这样的：

改造前后对比

改造前 改造后
全量拉取耗时 ~2 小时（经常中断） ~5 分钟
内存峰值 4GB+，经常 OOM < 200MB
中断恢复 从头开始 Redis 断点续传
单次评分耗时 秒级（扫全库） 微秒级（二分查找）
ES 压力 scroll 锁资源 普通查询，无状态

一些踩过的坑

1. search_after 的排序字段必须有唯一性。 如果你用 x_age 排序，大量相同值会导致分页结果重复或遗漏。用 _id 做排序字段最稳，它是全局唯一的。如果需要按 x_age 排序，可以加 _id 作为第二排序字段："sort": [{"x_age": "asc"}, {"_id": "asc"}]。

2. Redis 存游标时注意序列化。 search_after 返回的 sort 值是个数组，可能是 [1234, "doc_id"] 这种混合类型。存 Redis 前 JSON 序列化，取出来反序列化，别直接 str() 转换。

3. 压缩写入时注意 flush。 gzip.open 默认有缓冲区，如果进程意外退出，缓冲区里的数据会丢。可以定期 f.flush() 和 os.fsync()，或者接受最后几百条数据的丢失（反正有断点续传）。

4. 有序数组的刷新策略。 我们是按日刷新，凌晨跑一次全量构建。如果数据更新很频繁，可以考虑增量方案——新数据插入有序数组（用 insort），但要注意 400 万条的数组 insort 是 O(N) 的，频繁插入不合适。折中方案是每小时全量重建一次，或者用两次数组（历史有序 + 新增无序），查询时两边各查一次再合并。

写在最后

回过头看，这个方案没有什么特别高深的技术。search_after、bisect_right、Redis 存状态，都是现成的东西。关键在于把事情拆开想：

  • 离线能做的事，别放到在线做。
  • 能用无状态解决的，别用有状态。
  • 内存里只放必要的东西。
  • 进程随时可能死，设计时假设它下一秒就会死。

400 万条数据不算大，但如果方案不对，它也够你喝一壶的。希望这篇文章能帮到遇到类似问题的朋友。
